# Changelog

## Unreleased
- **Runtime model migration**: The factory's runtime now uses per-station models with claude-opus-5-5 for builders, claude-sonnet-5-5 for spec-writer/test-writer and most reviewers, and openai/gpt-6.1-sol for design stations (reviewer-design, reviewer-ux, builder on UI surfaces). Retired models claude-sonnet-4-5 (retires 2026-11-30) and openai/gpt-6-astra (retired 2026-11-03) are removed from standing wiring. Runtime dispatch is model-based: Anthropic models run through Claude Code print mode via the gateway Anthropic route; openai/gpt-6.1-sol runs through an agentic OpenAI runtime (Codex) via the gateway OpenAI route. Unknown models fail loudly with no fallback. The configured model and executed model must agree or the step fails; the executed model recorded in run reports comes from runtime evidence (what the runtime reports), never copied from the configured label. New dispatcher (tools/dispatch_station.py) routes to claude_station.py or codex_station.py based on model family. The three new models stay unpriced until a verifiable source is recorded; their steps record cost measured false with the reason. Review channel invariants hold for both runtimes: reviewers write exactly their own review file through the scoped channel; wrapper validation and one in-session correction behave the same. The report field astra_measured_tokens_total keeps its name (test suite pins it) with comments updated to say interface stations. Decision record at brain/decisions/0004-model-migration.md. Model route smoke script at tools/model_route_smoke.py probes the four routes (Anthropic text for claude-sonnet-5-5 and claude-opus-5-5, OpenAI text and vision for gpt-6.1-sol).
- Render crash tolerance: video line render wrapper (content/youtube-anvil-v2/blender/render_all.sh) now judges chunks by output files and DONE lines instead of exit codes, tolerates Blender crashes after work completes, prevents single chunk failures from aborting the queue, and runs up to 2 completion sweeps to recover missing frames. Per-chunk outcomes (clean_exit, tolerated_crash, requeued, failed) are recorded in frames/logs/outcome-*.json and aggregated into render-stats.json by tools/render_stats.py. Fixes intermittent Blender 4.5.15 exit crashes that killed two full renders of the wo-gh-18 film at 2,359 of 2,515 frames.
- Render crash tolerance loopback round 2: fixed film.py invocation to use all 6 arguments (section, total frames, outdir, resolution percent, first frame, last frame) restoring compatibility with frozen film.py interface; aligned outcome record and statistics script on "attempts" field; added section ID integer validation in both render_all.sh and render_stats.py to prevent path traversal; replaced heredoc JSON construction with proper json.dumps() encoding to prevent JSON injection; added VIDEO_CONTENT_DIR validation requiring existing directory with durations.json. Tests updated to match real film.py interface and pin the 6-argument invocation contract.
- Render crash tolerance tests: deterministic test suite (T1-T5) for the video line render wrapper's crash tolerance features, verifying output-based chunk judgment (not exit codes), queue continuation despite failures, completion sweeps for missing frame ranges, and per-chunk outcome statistics (clean_exit, tolerated_crash, requeued, failed). Tests drive render_all.sh with fake Blender binaries via BLENDER environment variable, requiring no real Blender installation.
- **Quality standard for visual deliverables**: A standing factory-level charter defines production quality per product type with observable criteria. For physical consumer products: materials (surfaces read as their actual materials), light (one coherent light story with consistent shadows and reflections), contact (objects meet surfaces with weight and pressure), and scale (size reads true against context and human anatomy). For game and illustration products, the project states its own standard in the design system using the same observable form. Reference anchors (owner-supplied boards under design/reference/) carry the quality bar into every visual run; the scaffolding creates the directory alongside design/DESIGN.md and never overwrites existing contents. reviewer-design and reviewer-ux contracts gain a quality section separate from compliance: the reviewer compares outputs against anchors and charter criteria, naming specific gaps by category, with a deliverable able to pass compliance yet fail quality in one run. The quality sections cite the anchor used in comparison or state "charter floor only" when no anchors available. Generating stations (builder, media-producer, brief-writer) verify each output against anchors and charter criteria before review runs per their station contracts, recording the comparison in run evidence (anchor cited, criteria checked, gaps found or explicit none). The composition order is anchors first, then design system and verified learnings, then charter floor; deliberately stylized anchors make stylized the bar. A visual run with no anchors proceeds under the charter floor alone with a visible warning in the report. Runs with no visual surfaces never receive the charter in any packet. For sets of related deliverables (multiple images of one product), the work order designates a canonical identity reference and enumerates identity traits the set must hold constant (finish, detail colors, mounting, proportions, markings for physical products; equivalents stated for other types). reviewer-design runs a same-subject test comparing every asset against the identity reference on each trait; any divergence fails the quality section with asset and trait named, even when each asset individually passes anchor comparison. Work order model gains anchors, identity_reference, identity_traits and deliverable_set fields with path traversal validation (rejects parent directory references, backslashes, absolute paths). Quality module wired into runner: packet_quality_charter_section and packet_anchor_section are called by packet_step and their results passed to _packet_text for imagery stations on visual runs. Control character sanitization protects work order controlled strings in packet output. Status page contrast fixed (secondary text reaches 4.5:1 against dark background) and responsive treatment added for mobile (sticky first column, touch-friendly scrollbar). Quality charter document at docs/QUALITY_CHARTER.md, implementation in anvil/quality.py, 37 tests (23 unit + 14 integration) covering scenarios S1-S7 from quality-standard spec.
- **Post-deploy health verification**: After a run's deploy step completes, the factory verifies the deployed application's health from live signals and records the outcome (healthy, unhealthy, or unknown) with the same honesty as every other verdict. Health verification runs for any run whose project declares a health target: the deployed base URL, key routes to check with expected HTTP statuses, and optionally a platform signal source (Cloudflare Workers analytics via API). Route checks record observed status or transport errors and latency; platform signals record request and error counts for the window since deploy. Healthy requires all route checks passing and platform errors within acceptable limits; unhealthy quotes failing signals in the record and forces the human gate with the health reason even when the approver verdict was approved; unknown (no target, or all signal sources failed to read) is never rendered or aggregated as healthy anywhere. The outcome lands in the run report's health section and modifies the deployment status (deployed and healthy, deployed and unhealthy, deployed with health unknown); the swimlane shows health as a step after deploy. Security hardening includes URL scheme validation (http/https only), SSRF protection (rejects private IPs, loopback, link-local including cloud metadata endpoints), input validation for API parameters (alphanumerics, hyphens, underscores only), HTTP status validation (100-599 range), and exception sanitization to prevent credential or topology leakage. Documentation warns against putting credentials in config files. Projects gain an opt-in application metrics slot in configuration (endpoint and provider_key fields, provider agnostic, no vendor names in factory core or generated configs). Onboard never overwrites existing configurations. Status page rendering includes responsive table handling with overflow containers and mobile media queries to prevent horizontal scrolling at 390x844. Demonstrated on a factory-owned target (status page or intake worker) with health evidence in the demonstration run's report. Supports scenarios S1-S7 from post-deploy-health spec.
- **Design knowledge base and UX module**: ANVIL's design work now runs through a two-layer UX module: a knowledge base layer (reference data for interface styles, color palettes by product type, font pairings, UX guidelines, and product type notes) and a guide layer (design stations that apply the knowledge base on the design model from the routing policy). The factory ships a starter knowledge dataset at design-knowledge/ authored for ANVIL in the factory's voice. Operators can supply runtime knowledge packs (directories outside the repo tree with manifest.json and data files) via work order fields; packs are validated at load, recorded in run reports as operator-supplied inputs, and never written to the project or factory tree. Product type matching is deterministic: the same project product type and pack always select the same slice (product type note, referenced styles/palettes/fonts, general guidelines). Design station packets (reviewer-design, builder for UI surfaces, design authoring paths) gain a Design knowledge section with the matched slice and an authority statement: the project's own design system (design/DESIGN.md, tokens.json) wins on any conflict, and a deviation from the knowledge base alone is never a finding. Design authoring contracts require citation of knowledge sources in DESIGN.md; reviewer-design names the entry behind any suggestion. The catalog marks guided design stations with the designation, and the runner applies the design model (openai/gpt-6-astra) from the routing policy to guided stations at runtime (reviewer-design and writer always; builder only for UI surface work). Supports scenarios S1-S10 from design-knowledge spec.
- Per job cost measurement: Each run step gains a cost record with measured flag, input and output token usage when reported, the model priced from, and the amount when measured. For stations executed by a runtime that leaves session transcripts with token usage, the executor sums the usage attributable to the step's execution window; usage that cannot be attributed to a step is not spread across steps. For HTTP gateway executions, the executor reads the usage object from the gateway response when present and attaches it. A step with no usage source, or an executed model with no price table entry, records measured false, a null amount, and the stated reason. The run report gains a cost section whose total is the sum of measured steps only, with measured and unmeasured step counts; the swimlane shows the total with its coverage counts. Prices live in configuration as a price table mapping model names to input and output prices per million tokens, every entry labelled with its source and the date recorded; the loader rejects an entry missing either label. Cost measurement changes no verdict: the approver, the gates and the human gate read nothing from the cost section. Supports scenarios S1-S5 from cost-measurement spec.
- **Rendered design review**: reviewer-design now judges screenshots of the built page at defined breakpoints, not just source code. Projects can declare a servable web page in anvil.yaml with serve command or static root, page path, and breakpoints (defaults 390x844 and 1440x900). After builder completes, the runner serves the project locally, captures PNG screenshots per breakpoint into runs/<id>/evidence/, and includes them in reviewer-design's packet with citation instructions for layout/spacing findings. When serving or capture fails, the review states that rendered evidence could not be captured and gives the reason. Run reports list screenshot evidence with paths. Configuration-driven, security-hardened (prevents command injection, path traversal, URL injection, validates dimensions, uses dynamic ports, cleans up process groups, sets secure evidence directory permissions). Factory's own status page serves as demonstration.
- **UX reviewer (reviewer-ux)**: A second design lens that judges user experience separately from visual system compliance. reviewer-ux evaluates four dimensions: user flows and task completion (can the primary task be started, followed and finished), usability heuristics (visibility of state, real-world match, user control, consistency, error prevention/recovery, recognition over recall), accessibility basics (labeled controls, focus visibility, contrast per design tokens, text alternatives, keyboard reachability), and interface copy clarity (labels, buttons and messages that say what they mean). The station explicitly excludes visual system compliance (tokens, type scale, palette) as reviewer-design's lens. reviewer-ux is a guided design station receiving the UX guidelines slice from the knowledge base, rendered evidence when screenshots exist, and the design model from routing policy. Added to the reviewer groups of sdlc-default, content-default and content-short pipelines. Routing activates reviewer-ux only when the work order carries a UI surface; on work with no UI surface it is routed out before execution with the surface rule named, and non-UI work pays nothing for the lens. Run reports and swimlanes list reviewer-design and reviewer-ux as separate entries with independent verdicts and findings. When no rendered screenshots exist, reviewer-ux states it judged from source and knowledge slice without rendered evidence.
- Risk and surface routing: A deterministic routing step runs after intake and before reviewers, selecting which reviewers run and which models are used based on the work order's risk rating and surfaces. Low risk work with no UI or security surface runs a reduced reviewer panel (reviewer-spec and reviewer-tests) at a cheaper configured model. Security surfaces always keep reviewer-security in the set at a strong model; UI surfaces keep reviewer-design. Medium and high risk work runs the full panel at policy models, with high risk explicitly recording no reduction applied. Null risk (unrated work) defaults to the full panel. Routing rules live in project configuration with a factory-shipped default table. The routing record (selected reviewers, routed out reviewers with reasons, model assignments, and decision rationale) is written to the run directory and rendered in the report with a dedicated section and swimlane summary. Routed out reviewers are recorded as expected absences, never counted as failures. The approver aggregates only the reviews from selected reviewers, and its verdict rule states the expected count after routing. Model routing policy defines a ceiling: routing may reduce models below the policy but never exceed it. Configuration loading validates all model assignments against the policy ceiling, validates reviewer lists contain only valid reviewer station IDs, and validates all model references exist in the model hierarchy; violations fail at load with the offending value named. Policy ceilings can be overridden in project configuration with factory defaults applied as fallback when absent. Routing trusts intake outcomes as authoritative (documented security consideration: intake owns risk assessment, routing owns panel selection). Gates (checks and scenario-to-test) are unaffected by routing and always run as configured. Supports scenarios S1-S7 from risk-routing spec.
- Intake outcomes: Intake can now reject, rescope, or park work orders with recorded reasons and questions. The work order model gains intake_outcome (outcome, reasons, questions, rescoped_description), risk rating (low/medium/high) and surfaces list. Rejected outcomes (harmful, deceptive or unlawful purposes) are terminal - the runner stops after intake, status becomes rejected, and no downstream stations execute. Rescoped outcomes rewrite the work order description to buildable scope with the cut recorded, and downstream packets carry the rescoped description. Waiting_info outcomes park work orders until questions are answered, status becomes waiting_info, and a later run can proceed from intake again. Accepted and rescoped work orders carry intake's risk rating and surfaces from the defined vocabulary (ui, security, data, payments, deploy, content, api). Run reports and swimlanes render rejected and waiting states honestly with reasons and questions shown. Intake station prompt documents all four outcomes, the refusal class, rescope discipline, and risk/surface vocabulary. Supports scenarios S1-S5 from intake-outcomes spec. Input validation enforces the intake outcome vocabulary (accepted, rejected, rescoped, waiting_info), risk levels (low, medium, high), and surfaces vocabulary (ui, security, data, payments, deploy, content, api), with required field validation for each outcome type (reasons for rejected, rescoped_description for rescoped, questions for waiting_info). Report rendering escapes markdown and HTML special characters in user-provided content (reasons, questions) and fences rescoped_description in code blocks to prevent content injection.
- Deterministic checks gate: a new station that runs project-configured check commands and validates protected paths before reviewers see the work and again before deploy. Check commands and protected paths are resolved from the base ref snapshot (never from builder-modified files), protected paths default to `tests/` and the checks config itself, and gate failures trigger loopback to the builder or block deployment. Runs twice per pipeline: pre-review (after builder, before reviewers) and pre-deploy (after approval, before deployer/publisher). Projects with no checks configured record the gate as `not_configured` and proceed normally. The gate is visible in the swimlane and fully recorded in the run report. Documentation: `docs/CHECKS-GATE.md`.
- Checks gate protected path semantics clarification: The gate judges only the builder station's changes for each attempt (working tree delta across builder execution), not cumulative changes from all stations. Builder modifications or deletions of base ref files under protected paths are violations; builder additions to protected paths are recorded as observations, not violations. Test-writer output (scenario tests written from the spec) is part of the judging apparatus, not the work under review. Each attempt is judged on its own delta. The gate output records the basis judged (builder_delta with attempt number) and observed additions.
- Checks gate CLI base ref derivation: When running in a git repository, the CLI automatically derives the base ref as the merge base of HEAD and the project's base branch (configurable via `base_branch` in anvil.json, defaulting to the repository's default branch). The `anvil run` command accepts `--base-ref` to override automatic derivation. The base ref used is recorded in the run report for auditable configuration provenance. This ensures the S4 control (base ref resolution) is wired through the CLI execution path, not only the module API.
- Review producer: reviewer stations write their own review file at `runs/<work-order-id>/<station-id>.review.json`. The runner never transcribes executor output to the review file; it reads the file the reviewer wrote. Before a reviewer step executes, the runner removes any pre-existing review file at that path so presence at exit means produced in this run. Missing review files record `review_file_missing` (distinct from `review_parse_failed`) in the step envelope, and the station contributes zero reviews. The wrapper validates the review file at station exit and allows one in-session correction attempt when the file is missing or malformed; a second failure stands as recorded. Path validation prevents work order IDs or station IDs with path separators or parent references from escaping the intended directory. Reviewers use Edit, Write and NotebookEdit tools are disallowed for reviewer stations; reviewers write the review file via Bash.
- Review parsing integrity: one authoritative review channel per reviewer station step (`runs/<work-order-id>/<station-id>.review.json`), whole document parse (no scanning), fail closed on malformed reviews with `review_parse_failed` in the step envelope, and approver rule states both counted and expected numbers when counted reviews are fewer than expected. Reviewer packets and prompts updated to name the review file path and state the complete answer is exactly one review JSON object. Verdict vocabulary standardized to pass, fail, changes_requested across all reviewer stations.
- Project design systems: Every project can define its own design system at design/DESIGN.md (brand identity, art direction, component rules, motion rules, quality bars) and design/tokens.json (machine-readable token values). Scaffolded by anvil init, anvil new-project and anvil onboard; never overwrites existing files. Interface-producing station packets (builder, writer, media-producer, brief-writer, reviewer-design) carry a Project design section with tokens and quality bars. New reviewer-design station judges interface output against the project's design system; added to sdlc-default, content-default and content-short pipelines. Missing design systems produce run warnings and reviewer-design findings instead of silent passes.
- Verified memory gate: brain/learnings.md is a verified store behind a provenance check. Proposals wait quarantined in brain/inbox/ and are promoted only when deterministic code confirms the cited run report exists, the cited artifact exists, and the evidence matches the report. Packets carry a Verified learnings section sourced only from non demoted verified entries; demotions are recorded as decisions. New commands: check-brain, promote-learning, demote-learning.
- Bounded supervisor: a 24th station that runs between runs. Deterministic stall signals over the run record (repeated reviewer fails, exhausted loopbacks, repeated no_reviews, deployed_unverified) trigger a supervisor packet; executed proposals are validated against the catalog plus a constitution (intake, approver and triage-human required, reviewer coverage may not shrink) and filed under pipelines/proposals/. Nothing auto applies.
- Model provenance: every step and envelope records configured_model in all modes; executed steps record executed_model and an executor object {kind, detail}. An http executor's executed model is its configured endpoint model; a command runtime's model is recorded only when its own output reports one, never guessed. The status page shows the model under each station name.
- Agent execution: `anvil run --execute` with a `runtime` object in anvil.yaml. Command executors (shell template with {packet} and {output}) and HTTP executors (OpenAI style endpoint, key from a named environment variable) run station packets, write output artifacts, and record reported usage tokens while cost stays null unless reported.
- Run scoped approver: the approver now aggregates only reviews produced during the same run. A run whose reviewers only produce packets ends with verdict no_reviews; standing project reviews remain the record read by `anvil check`.
- Automatic deploy and verification: a `deploy` object in anvil.yaml lets an approved execute mode run with no human gate blocking run its deploy command, then a deterministic verification gate. Deployment status is reported as deployed_verified, deployed_unverified or deploy_failed, with verify findings written for failed verification.
- Intake worker: POST /github accepts GitHub webhook deliveries for issues, with optional HMAC signature verification through GITHUB_WEBHOOK_SECRET, mapping opened or anvil labeled issues to work orders.
- Run status page: `anvil status-page <project>` renders every run report in a project into one self contained HTML page (Arananet style, inline CSS, no external assets) for Cloudflare Pages, GitHub Pages or any static host, with skipped unreadable runs noted in the footer.
- **Status dashboard lifecycle stages**: The status page now shows a lifecycle board with each work order's stage progression. Stages (SPEC, BUILD, REVIEW, APPROVED, MERGED) are derived from evidence in run reports: spec-writer executed for SPEC, builder executed for BUILD, reviewer steps executed for REVIEW, approved verdict for APPROVED, and merge records for MERGED. Intake states (PARKED from waiting_info verdict, REJECTED from rejected verdict) are shown instead of stage progression when applicable. NEEDS HUMAN badge appears when decision.human_gate.required is true. The board is one row per work order with ID (as a real anchor link to the detailed run section), title, stage sequence showing reached stages marked and current stage highlighted, reproducible from the same data, and generated from run reports plus merge_records/ data with no network calls or inference. Board styling uses a consistent spacing scale defined via CSS custom properties, adapts to narrow viewports (below 400px) without horizontal scrolling via flex-wrap, and all text/background pairs meet WCAG 4.5:1 contrast minimums for accessibility. Supports scenarios S1-S9 from status-lifecycle-stages spec.
