## Purpose

The factory remembers inside a project and forgets between projects. A project's brain holds its verified learnings and its practices; the curated skills hold craft; a blueprint names a stack. Nothing holds the thing a finished project proves: the shape that worked for that kind of product, the routes that were tried and rejected, and what each stage really cost.

The case that shows the gap is Retro Explainers, a channel of short explainer videos that began as a draft from this factory and was then developed in its own repository between 2026-11-15 and 2026-11-22 (handover note of 2026-11-22, operator copy). In one week that project settled a gated stage order (script, proof, master, pack), deterministic checks that run before any reviewer sees an output, an independent reviewer limited to one automatic revision, a needs-owner stop, cost measured per stage, a board that tracks every episode, and five visual routes that were each built, rejected and are now banned and checked by a tool. Four episodes are published. None of it has come back to the factory: the next project of that kind would pay again to explore the five rejected routes, and the factory itself only now has a board (wo-gh-47) and futile loop stops (wo-gh-49) that the child project already had. Owner direction of 2026-11-22: the factory must learn from projects that succeeded instead of exploring again and consuming tokens again.

This order gives the factory a place for that knowledge and a discipline for letting it in. A pattern is a versioned pack, in plain files in the repository, harvested from a project that succeeded, held in quarantine until the owner promotes it, selected deterministically for a new project by its product type, and handed to each station as the slice that station needs. Plain files and no database: a pack is reviewed like any change, and a person who copies the factory gets the patterns with it.

## Terms
- pack: the files of one pattern version, per R1.
- proposal: a pack skeleton plus harvested files under patterns/inbox/<id>/, written by harvest (R2), not yet promoted.
- promoted pack: a pack at patterns/<id>/ written by promote-pattern (R3). Only promoted packs are ever selected.
- open marker: a JSON string value, or a line in a markdown file, that begins with the literal text `OPEN:` followed by what must be decided. A field holding an open marker is an open field.
- budget tokens: the figure token budgets read, per decision 0017 (cache reads counted at efficiency.cache_read_weight). raw tokens: the counts usage artifacts record.

## Requirements

### R1. The pattern pack
- R1.1: A pack is a directory holding: pattern.json; structure.md; dead-ends.json; calibration.json; optionally guardrails/ (check scripts, in the check pack form of the blueprint guardrails order when that lands; until then any file a command line can run); optionally skills.json (a JSON list of curated skill ids the pattern relies on); and, for a promoted pack, provenance.json and source/ (R2.2) and promotion.json (R3.1). No other top level entry is allowed.
- R1.2: pattern.json is a JSON object with these required fields: id (string matching `^[a-z0-9][a-z0-9-]*$`, equal to the directory name), title (non-empty string), version (string of one to three dot separated non-negative integers, for example "1" or "1.2.0", compared numerically part by part with missing parts read as 0), product_types (non-empty list of non-empty strings), blueprint (string naming a directory under blueprints/, or null), source (object with project, a non-empty string, and commits, a non-empty list of full 40 character commit ids) and success_evidence (non-empty list; each entry an object with kind, one of owner_acceptance, merged_change, published_artifact, and reference, a non-empty string naming the record, the change or the published URL).
- R1.3: dead-ends.json is a JSON list; each entry is an object with id (unique within the file), route (what was tried), why (why it was rejected), evidence (non-empty string naming the record, commit, run or review that shows it) and enforcement, one of "check" or "prompt". An entry with enforcement "check" also carries check, the path of a file under the pack's guardrails/ that exists; an entry with enforcement "prompt" carries no check.
- R1.4: calibration.json is a JSON object with figures, a list; each figure is an object with stage (stage or station name), metric (one of tokens, cost_usd, wall_seconds), value (non-negative number) and source (non-empty string naming the run, usage artifact or record it came from). A figure whose metric is tokens also carries unit, one of "raw" or "budget"; a figure with unit "budget" also carries cache_read_weight, a number from 0 to 1. All budget figures of one calibration.json carry the same cache_read_weight.
- R1.5: Loading a pack (anvil/patterns.py) validates R1.1 to R1.4 and fails with an error that names the pack, the file and the entry (the dead end id, or the figure's stage and metric) for: a missing required file or field, a value of the wrong type or outside its set, a dead end without evidence, a calibration figure without source, a token figure without unit, a budget figure without cache_read_weight, or a check that does not exist. Ids are unique across all promoted packs; a second pack with an id already loaded fails loading naming both directories.
- R1.6: The content rule: a pack carries process, guardrails, dead ends and measurements and never a project's content or identity. Validation rejects, naming the file: a file with one of the extensions .png .jpg .jpeg .gif .webp .bmp .ico .svg .mp4 .mov .webm .mkv .mp3 .wav .ogg .flac .ttf .otf .woff .woff2 .psd .ai .sketch .fig .pdf .zip; any file whose first 8192 bytes contain a NUL byte; a file named like a secret (.env or .env.*, *.pem, *.key, *.p12, or a name containing "secret", "credential" or "password", case insensitive); and a design token file (a file named tokens.json, design-tokens.json or *.tokens.json, or the project's design token file named in the harvest manifest). When the harvest manifest names the source project's design token file, harvest records every string value of length 4 or more from it in the proposal's provenance.json as forbidden_values, and validation fails a pack whose structure.md, dead-ends.json or any file under source/ contains one of them, naming the file and the value. Copy (prose, scripts of the product) that none of these rules detects is held by the owner at promotion; the validator does not claim to detect it and docs/PATTERNS.md says so.

### R2. Harvest into quarantine
- R2.1: `anvil harvest <project-path> --as <pattern-id> [--manifest <file>]` reads a project on disk. The manifest defaults to <project-path>/anvil-harvest.json and is a JSON object with files (non-empty list of paths relative to the project), provenance (one of "line" or "outside_line") and optionally design_tokens (a path relative to the project). A missing or malformed manifest, an absolute path or a path that leaves the project, a listed file that does not exist, or a listed file with uncommitted changes refuses with exit code 1 and a message naming the cause; nothing is written.
- R2.2: On success harvest writes patterns/inbox/<pattern-id>/ holding source/<relative path> for each listed file (byte identical copy), provenance.json and the skeleton files pattern.json, structure.md, dead-ends.json and calibration.json. provenance.json carries project (the absolute project path as given), head (the project's HEAD commit), provenance (the manifest value), forbidden_values (R1.6, an empty list when no design_tokens) and files, one entry per copied file with path, commit (the last commit that touched the file, from git) and sha256 (of the copied bytes). The skeleton sets id to <pattern-id>, source.commits to [head], and every field that needs judgment (title, version, product_types, blueprint, success_evidence, every dead end, every figure, structure.md body) to an open marker.
- R2.3: Harvest is deterministic (two runs on the same project, commit and manifest write byte identical proposals) and makes no model call and no network call. An existing patterns/inbox/<pattern-id>/ is refused, not overwritten.
- R2.4: provenance.json states in a field provenance_note, in one sentence, whether the line produced and reviewed the source work ("line") or it was authored outside the line ("outside_line"), per decision 0006.
- R2.5: Nothing under patterns/inbox/ is ever loaded by selection (R4), injected into a packet (R5) or used by init --pattern (R5.4); init --pattern with an id that exists only in the inbox refuses naming it as unpromoted.

### R3. Promotion is the owner's, on evidence
- R3.1: `anvil promote-pattern <pattern-id> --by <name>` promotes patterns/inbox/<pattern-id>/ only when all of these hold: no open marker remains in any pack file; every file listed in provenance.json exists under source/ and matches its recorded sha256; success_evidence holds at least one entry of the R1.2 kinds with a non-empty reference; the pack passes R1.5 and R1.6; and, when patterns/<pattern-id>/ exists, the proposal's version is higher than the promoted one. On success the proposal moves to patterns/<pattern-id>/, promotion.json records by, the date (UTC, YYYY-MM-DD) and the version, and the inbox entry no longer exists. Otherwise it exits 1, lists every unmet condition (each open field by file and field or line, each changed or missing file by path, the missing evidence, each content rule violation, the version conflict) and changes nothing on disk.
- R3.2: When a version is promoted over an existing one, the previous pack is moved, unchanged, to patterns/<pattern-id>/history/<previous-version>/ (history/ is the one extra entry R1.1 allows in a promoted pack). Packs under history/ are never selected; they stay on record.
- R3.3: `anvil check-patterns` loads and validates every promoted pack under patterns/ (inbox and history excluded), prints one line per pack with id, version and the count of dead ends enforced by a check and enforced by prompt text, and exits 0 when all pass and 1 naming each failure otherwise. With no promoted pack it prints that none exist and exits 0. It is a command the factory's checks can run; adding it to anvil.json is not part of this order (anvil.json is protected).

### R4. Selection is deterministic
- R4.1: The project's product type is read where it is today (anvil/knowledge.py get_project_product_type, the line "Product type:" of brain/project.md). Candidates are the promoted packs whose product_types contain that value exactly.
- R4.2: With more than one candidate the winner is decided in this order: most specific (fewest entries in product_types), then highest version, then lowest id in plain string order. The selection records which of these three decided ("only candidate", "most specific", "highest version", "id order").
- R4.3: The run report (report.json) carries a top level key pattern: {"id", "version", "rule"} when one is selected, and {"id": null, "version": null, "rule": "<why none: no product type declared, or no promoted pattern serves <type>>"} otherwise. The same project and the same patterns/ always produce the same value. Selection adds no event kind; the events contract is unchanged.
- R4.4: When none is selected, nothing is injected and every packet is byte identical to what the same run produces without this change.

### R5. Each station gets its slice
- R5.1: When a pattern is selected: spec-writer and builder packets gain a section headed `## Proven pattern` holding the title, version, structure.md and each dead end (route, why, evidence, enforcement); every reviewer-* packet gains a section headed `## Proven pattern: dead ends to check` listing each dead end as a statement the change must not reintroduce; the intake packet gains one line `Proven pattern: <title> <version>`. No other station's packet changes.
- R5.2: Each section carries the authority sentence of R6.1.
- R5.3: Packet budgets apply. The existing trim order (compact tokens, reduced quality bars, learnings limited) is unchanged and runs first; if the packet is still over budget, one further trim reduces the pattern section to title, version and each dead end's route and why (structure.md and evidence dropped). The step's action is recorded as trimmed as today, and the step record also carries pattern_trimmed: true. Over budget policy fail behaves as today.
- R5.4: `anvil init <path> --name <name> --pattern <id>` creates everything the default init creates and in addition: the pack's structure.md copied to the new project's brain/pattern.md; the pack's guardrails/ copied to the new project's guardrails/<id>/; one command per check (each dead end with enforcement "check") appended to the "checks" list of the new project's anvil.json, created if absent; the line "Product type: <first entry of product_types>" in brain/project.md; and, from calibration.json, efficiency.station_budgets in the new project's anvil.yaml set to the budget figures whose stage is a station id of the default pipeline, with efficiency.cache_read_weight set to their weight. Raw token figures are not converted and are not written; init prints which figures it skipped and why. An unknown or unpromoted id refuses with exit 1 before anything is written.
- R5.5: The dead ends enforced by a check and those that are prompt text only are counted per pack by check-patterns (R3.3) and listed with their enforcement in the packet sections of R5.1.

### R6. The authority order
- R6.1: The project's own brain, practices and specs win over a pattern on any conflict; a deviation from a pattern alone is not a finding. A pattern is reference the project starts from, the same standing the design knowledge has. The packet sections of R5.1 say so in one sentence.

### R7. Regression tests

Runs use a fake runtime (no network, no real model) in the manner of tests/test_continuous_run_accounting.py.
- R7.2: Any test asserting a fact about this order's own run (the tree against the base ref, files untouched) carries the guard of decision 0018 (skip unless ANVIL_WORK_ORDER_ID equals wo-gh-50) so tests/test_run_evidence_scoping.py passes. No test compares wall clock figures between two runs for equality.
- R7.3: The full factory suite (python -m unittest discover -s tests -p 'test_*.py') passes with the new files added and no test file present at the base ref modified or deleted.

### R8. Builder report

It states the base ref it verified the tree against (13244db35475b9a19dbd041bc69cf6487d806a45), the exact full factory test count from the suite run, and the names of the new test files added.

## Scenarios

### Scenario: A pack must show its evidence
- S1 (R1.2, R1.3, R1.4, R1.5, R7.1): Given a fixture pack whose dead end "dither-overlay" has evidence "", when it loads, then loading fails with a message containing "dead-ends.json" and "dither-overlay". Given a pack whose figure {stage: "builder", metric: "tokens", value: 900000, unit: "budget", cache_read_weight: 0.1} has no source, then loading fails naming "calibration.json", "builder" and "tokens". Given a token figure without unit, or a budget figure without cache_read_weight, loading fails naming the figure. Given two packs with id "explainer-video", loading fails naming both directories. Given a complete pack, it loads.

### Scenario: A pack never carries the source project's identity
- S2 (R1.6, R7.1): Given a pack holding guardrails/logo.png, or source/.env, or source/design-tokens.json, validation fails naming that file. Given a harvest manifest whose design_tokens file holds {"brand": "#1A2B3C"} and a structure.md that contains "#1A2B3C", validation fails naming structure.md and "#1A2B3C". A pack without them passes.

### Scenario: Harvest proposes, with provenance
- S3 (R2.1, R2.2, R2.3, R2.4, R7.1): Given a fixture git project with two commits and anvil-harvest.json listing docs/stages.md and tools/check_routes.py with provenance "outside_line", when `anvil harvest <project> --as explainer-video` runs, then patterns/inbox/explainer-video/ holds source/docs/stages.md and source/tools/check_routes.py byte identical to the originals, provenance.json lists each with path, its last commit and the sha256 of its bytes, provenance is "outside_line", and pattern.json title, version, product_types and success_evidence each begin with "OPEN:"; the fake runtime and any network function record zero calls; a second harvest into a fresh patterns/ produces byte identical files; a second harvest with the same id refuses. A manifest listing ../outside.md, or a listed file with uncommitted edits, refuses with exit 1 and writes nothing.

### Scenario: Quarantine holds
- S4 (R2.5, R4.3, R4.4, R7.1): Given a complete proposal in patterns/inbox/explainer-video/ serving "explainer-video" and no promoted pack, when a project whose brain/project.md says "Product type: explainer-video" runs, then report.json pattern.id is null and every packet is byte identical to the same run with patterns/ absent; and init --pattern explainer-video refuses naming the pattern as unpromoted.

### Scenario: Promotion needs evidence
- S5 (R3.1, R3.2, R3.3, R7.1): Given a proposal with version "OPEN: pick a version", promote-pattern refuses naming pattern.json and version and changes nothing on disk. Given a proposal whose source/docs/stages.md was edited after harvest, it refuses naming that path. Given a proposal with an empty success_evidence, it refuses naming success_evidence. Given a complete proposal, `anvil promote-pattern explainer-video --by owner` exits 0, patterns/explainer-video/promotion.json records by "owner" and the version, the inbox entry is gone, and check-patterns exits 0 printing "explainer-video" with its version and its check and prompt counts. Given a later harvest and promotion of version "2", the version "1" pack is at patterns/explainer-video/history/1/ unchanged; promoting version "1" again over "2" refuses.

### Scenario: Selection is deterministic and recorded
- S6 (R4.1, R4.2, R4.3, R7.1): Given promoted packs "video-a" (version "1", product_types ["explainer-video"]) and "video-b" (version "3", product_types ["explainer-video", "short-video"]), when a project with "Product type: explainer-video" runs twice, then both report.json files carry pattern {"id": "video-a", "version": "1", "rule": "most specific"}. Given two packs both serving only that type at versions "1.2" and "1.10", the "1.10" pack wins with rule "highest version". Given a project with no "Product type:" line, pattern.id is null and rule names the missing product type.

### Scenario: Each station gets its slice
- S7 (R5.1, R5.2, R5.3, R6.1, R7.1): Given a project matching promoted pack "video-a" with dead end "dither-overlay", when its packets are built, then the spec-writer and builder packets contain "## Proven pattern", the structure.md text and "dither-overlay"; each reviewer-* packet contains "## Proven pattern: dead ends to check" and "dither-overlay"; the intake packet contains "Proven pattern: " followed by the title and "1"; each section contains the authority sentence; and the packets of a project with "Product type: landing-page" are byte identical to those built with patterns/ absent. Given a builder packet budget that the packet exceeds only by the pattern's structure.md, the step action is trimmed, pattern_trimmed is true, and the packet still names "dither-overlay" without the structure.md text.

### Scenario: A new project is born from a pattern
- S8 (R5.4, R5.5, R7.1): Given promoted pack "video-a" with guardrails/check_routes.py, one dead end enforced by it and one by prompt, and calibration figures {builder, tokens, 900000, budget, 0.1} and {intake, tokens, 300000, raw}, when `anvil init <tmp>/new --name New --pattern video-a` runs, then <tmp>/new/brain/pattern.md equals the pack's structure.md, <tmp>/new/guardrails/video-a/check_routes.py exists, the new anvil.json "checks" list contains one command running it, brain/project.md contains "Product type: explainer-video", anvil.yaml sets efficiency.station_budgets.builder to 900000 and efficiency.cache_read_weight to 0.1, and init's output names the intake raw figure as skipped. Given --pattern nope, init exits 1 and <tmp>/new does not exist.

### Scenario: No pattern, no change
- S9 (R4.4, R5.4, R7.1): Given an init without --pattern, when the project is scaffolded, then its file tree and every file's bytes equal those of the default init at the base ref (the existing tests/test_greenfield.py and tests/test_onboard.py pass unmodified); and a run of a project matching no pattern produces the same packets, the same event kind sequence and the same report keys as before this change apart from the added pattern key.

### Scenario: The factory stays green and the report is complete
- S10 (R7.2, R7.3, R8.1, R8.2): Given the finished change, when the full suite runs, then it passes with no base ref test file modified or deleted, tests/test_run_evidence_scoping.py passes, "retry" does not occur in anvil/runner.py, and the builder report contains proven-patterns, promote-pattern, dead-ends.json, calibration.json, the base ref 13244db35475b9a19dbd041bc69cf6487d806a45, the test count and the new test file names.

## Out of scope
- Any promoted pattern. The first harvest, from Retro Explainers, is done by the operator with the tool once it exists; its promotion is the owner's.
- Adding check-patterns to the factory's own anvil.json checks (protected path; the owner may do so later).
- Detecting product copy beyond the R1.6 rules; selecting a pattern by anything other than the declared product type; converting raw token figures into budget tokens; changes to blueprints, the design knowledge loader, the memory gate, the practices door, the curated skills catalog, packet budget semantics or the events contract.
- Merging, publishing or deploying anything: the run stops at the owner human gate.

## Guardrails
- Python standard library only (git is called through subprocess, as the factory already does). No new dependency and no database.
- No em dash or en dash character in any produced file (project style rule).
- Relationships: a blueprint names a stack and a pattern names a proven project shape and may build on a blueprint; practices are review rules inside one project and patterns carry knowledge between projects; the blueprint guardrails draft defines the check pack format a pattern may carry, and each works without the other.
