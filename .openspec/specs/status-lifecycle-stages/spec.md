# Status Dashboard Lifecycle Stages

Status: approved
Slug: status-lifecycle-stages

## Roles
- implementer: builds the change described here
- reviewer: checks the change against this spec
- qa: checks the scenarios below with tests
- product_owner: owns the purpose and accepts the result

## Purpose
The status dashboard answers "what has the factory produced" but not the question a reader actually brings: where is each job right now. This spec gives the dashboard a lifecycle board: one at a glance page listing every work order, one row per job, with the job's stage progression readable in the row itself, refreshed from the latest run data each time the page is generated. The stages are read from evidence and nothing else, because a board that flatters the factory is worse than no board.

## Requirements
- The stage vocabulary is fixed: SPEC, BUILD, REVIEW, APPROVED, MERGED, in that order, plus the state NEEDS HUMAN which can attach to a job at any point its current run's decision requires a human. The intake states from the intake outcomes capability (waiting_info shown as PARKED, rejected shown as REJECTED) compose with the model: a parked or rejected work order shows that state instead of a stage progression it never entered or has left.
- Every stage is derived from evidence in the job's latest run data:
  - SPEC: the run report records the spec stage (the spec-writer step executed, or the run's stage data names spec complete).
  - BUILD: the run report records the builder step executed.
  - REVIEW: the run report records at least one reviewer step executed.
  - APPROVED: the run report's decision carries the approver verdict approved.
  - NEEDS HUMAN: the run report's decision carries human_required true, for any reason the gate set it (the human gate education and the risk overrides included, since they all land in the same flag).
  - MERGED: only an actual merge record for the work order: a merged pull request or a merged run branch recorded in the merge data the generator consumes. A verdict of approved is never read as merged; the human merge is the final gate, and an approved job with no merge record shows APPROVED.
- A job's current stage is the furthest stage its evidence supports, with NEEDS HUMAN overlaid whenever its flag is set on the latest run, and PARKED or REJECTED shown when the latest run ended in either intake state. A job with no runs yet shows its first stage as not yet started rather than inventing progress.
- Presentation: the generated page is a single board. Each work order is one row. The row carries the work order's identity (id and title), its stage progression rendered as the stage sequence with the stages reached marked, the current stage highlighted, and NEEDS HUMAN rendered visually prominent when it applies (its own badge treatment, not a footnote). The swimlane for the job stays one click away: each row links to the job's existing swimlane or run detail exactly as the dashboard already links run artifacts. The board is regenerated from the latest run data whenever the dashboard is generated; it holds no hand maintained state, and generating it twice from the same run data produces the same board.
- The change applies to the factory's dashboard generation (the status page generator), so every surface generated by it (the factory's own status page and the example project's page, which uses the same generator) renders the board the same way.
- Derivation is a pure function of the run data and merge data handed to the generator: the generator reads reports and merge records, it does not call the network, query a forge, or infer merges from branch names or commit messages.

## Scenarios

### Scenario: Stages derive from the run report's evidence
- S1: Given fixture run reports that record spec, builder and reviewer steps without an approver decision, when the board data is derived, then a job whose latest report shows all three step groups carries current stage REVIEW, a job whose latest report shows only the spec step carries SPEC, and a job with no runs shows no stage reached.

### Scenario: Approved is not merged
- S2: Given a fixture report whose decision verdict is approved and no merge record for that work order, when the board is derived and rendered, then the job shows APPROVED as its current stage and MERGED is not marked reached; and given the same fixture plus a merge record, then the job shows MERGED.

### Scenario: Needs human comes from the decision object
- S3: Given a fixture report whose decision carries human_required true, when the board is derived and rendered, then the job shows the NEEDS HUMAN state with its prominent treatment alongside its current stage, whatever stage that is; and given human_required false, then no NEEDS HUMAN state appears for the job.

### Scenario: Intake states compose with the stage model
- S4: Given a fixture report for a run that ended parked (waiting_info) and one that ended rejected, when the board is derived, then those jobs show PARKED and REJECTED respectively instead of a stage progression.

### Scenario: One row per job, progression in the row, swimlane one click away
- S5: Given a generated dashboard page from fixture data with several work orders, when the page is read, then each work order appears as exactly one row containing its stage sequence with reached stages marked and its current stage highlighted, each row links to that job's swimlane or run detail, and regenerating from the same data produces the same board.
